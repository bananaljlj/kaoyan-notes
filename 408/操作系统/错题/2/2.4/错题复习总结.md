## 二、核心知识框架

### 1. 死锁、饥饿与无限循环

死锁是指多个进程因竞争资源而相互等待，若无外力干预，这些进程都无法继续推进。

| 现象     | 形成原因                 | 进程能否自行恢复 | 典型特征                               |
| -------- | ------------------------ | ---------------- | -------------------------------------- |
| 死锁     | 一组进程形成资源等待闭环 | 不能             | 参与者都无法推进                       |
| 饥饿     | 资源分配长期不公平       | 理论上可能       | 其他进程仍在推进，某进程一直等不到机会 |
| 无限循环 | 程序控制逻辑错误         | 通常不能正常结束 | 不一定涉及资源等待                     |

死锁强调“一组进程互相等”，饥饿强调“某个进程一直抢不到”。第 20、23 题都在考这一差别。

### 2. 死锁的四个必要条件

死锁发生时，以下四个条件必须同时成立：

| 必要条件   | 含义                             | 常见破坏方法                                   |
| ---------- | -------------------------------- | ---------------------------------------------- |
| 互斥       | 资源一次只能被一个进程使用       | 将资源改造成可共享资源，如假脱机打印           |
| 请求并保持 | 进程保持已有资源，同时申请新资源 | 一次性申请全部资源；申请新资源前先释放已有资源 |
| 不剥夺     | 已分配资源只能由持有者主动释放   | 允许系统剥夺进程已经获得的资源                 |
| 循环等待   | 存在进程—资源的环形等待链       | 对资源统一编号并按递增顺序申请                 |

必须记住：

```text
死锁发生        → 四个必要条件一定同时成立
破坏任意一个条件 → 可以预防死锁
四个条件都成立   → 仍只能说“可能死锁”，不是一般情况下的充分条件
```

### 3. 预防、避免、检测与解除

| 方法     | 介入时机           | 核心思想               | 代表做法                           | 是否允许系统进入不安全状态 |
| -------- | ------------------ | ---------------------- | ---------------------------------- | -------------------------- |
| 死锁预防 | 资源分配规则设计时 | 破坏四个必要条件之一   | 一次性分配、资源有序分配、允许剥夺 | 不讨论安全序列             |
| 死锁避免 | 每次分配资源前     | 试分配后仍保持安全状态 | 银行家算法                         | 不允许                     |
| 死锁检测 | 资源已经按需分配后 | 定期判断是否已经死锁   | 资源分配图化简、检测算法           | 允许                       |
| 死锁解除 | 已检测出死锁后     | 打破已经形成的等待关系 | 撤销进程、剥夺资源                 | 已经发生死锁               |

容易混淆的归类：

```text
限制申请资源的顺序 → 预防：破坏循环等待
银行家算法         → 避免：保证分配后仍安全
死锁定理           → 检测：化简资源分配图
撤销进程/剥夺资源  → 解除：处理已经发生的死锁
```

### 4. 安全状态、不安全状态与死锁状态

若系统能找到一个进程执行顺序，使每个进程都能依次得到所需资源、完成并释放资源，则这个顺序是**安全序列**，系统处于安全状态。

三者关系为：

```text
安全状态   → 一定不会死锁
不安全状态 → 可能发生死锁，但此刻未必已经死锁
死锁状态   → 一定是不安全状态
```

因此，银行家算法不是检查“当前是否已经死锁”，而是在每次分配前检查“分配后是否仍有安全序列”，从源头避免系统进入不安全状态。

### 5. 银行家算法

银行家算法维护四组数据：

| 数据结构       | 含义                                              |
| -------------- | ------------------------------------------------- |
| `Available`  | 当前每类资源的可用数量                            |
| `Max`        | 每个进程对每类资源的最大需求                      |
| `Allocation` | 当前已经分配给每个进程的资源                      |
| `Need`       | 每个进程还需要的资源，`Need = Max - Allocation` |

收到进程 `Pi` 的请求 `Request_i` 后，依次检查：

1. `Request_i <= Need_i`，否则进程申请超过其声明的最大需求；
2. `Request_i <= Available`，否则当前资源不足，进程必须等待；
3. 假设完成分配，更新 `Available`、`Allocation_i` 和 `Need_i`；
4. 执行安全性检查，只有仍存在安全序列时才正式分配。

安全性检查的核心是反复寻找满足 `Need_i <= Work` 的未完成进程。假设它完成后执行：

```text
Work = Work + Allocation_i
```

若最终所有进程都能标记为完成，则系统安全；否则试分配会使系统进入不安全状态，应回滚并让请求者等待。

### 6. 资源分配图

资源分配图是描述某一时刻进程与资源状态的有向图：

- 圆形节点表示进程；
- 矩形节点表示一类资源；
- 资源框中的圆点表示该类资源的实例；
- `进程 → 资源类` 是请求边；
- `资源实例 → 进程` 是分配边。

环路与死锁的关系：

| 图中情况                       | 能否判断死锁                         |
| ------------------------------ | ------------------------------------ |
| 没有环路                       | 一定没有死锁                         |
| 有环路，且每类资源只有一个实例 | 一定发生死锁                         |
| 有环路，但某些资源有多个实例   | 可能死锁，也可能不死锁，需进一步检测 |

所以一般情况下：

```text
死锁 → 资源分配图中一定有环
有环 → 不一定死锁
单实例资源系统中：有环 ↔ 死锁
```

### 7. 死锁定理与资源分配图化简

死锁定理用于**检测死锁**。化简过程如下：

1. 找到一个当前请求能够被剩余资源满足的进程；
2. 假设该进程获得资源并顺利完成；
3. 删除它的所有请求边和分配边，相当于释放其占有资源；
4. 重复上述过程，直到无法继续化简。

若图能删去所有边，使所有进程成为孤立节点，则图可完全化简，系统没有死锁；若最后仍有无法删去的边，则相应进程处于死锁状态。

### 8. 同类资源数量与免死锁公式

设有 `n` 个进程竞争同一类资源，每个进程最多需要 `k` 个。最坏情况下，每个进程都先占有 `k-1` 个并再申请 1 个。要保证至少还能让一个进程完成，资源总数 `m` 应满足：

```text
m >= n(k - 1) + 1
```

等价地，在资源数 `m`、每个进程最大需求 `k` 已知时，保证不会死锁的最大进程数为：

```text
n <= floor((m - 1) / (k - 1))
```

不要把“资源不足”直接等同于死锁。资源不足只会增加竞争和等待；只有等待关系满足死锁条件时才会形成死锁。

### 9. 哲学家就餐问题

若所有哲学家都按同一顺序先拿左筷子、再拿右筷子，可能出现每人持有一支筷子并等待另一支的环路。

常见解决方案：

- 最多允许 `N-1` 位哲学家同时尝试取筷子；
- 只有两支筷子都可用时才一次取得；
- 奇偶号哲学家按相反顺序取筷子；
- 对筷子编号，始终先申请编号小的筷子。

限制最多 `N-1` 人进入取筷阶段后，无法形成所有人各占一支的闭环，因而预防死锁。注意：某种方案能预防死锁，并不自动说明它能保证公平、杜绝饥饿。

### 10. 资源剥夺与受害者选择

允许剥夺资源可以用于预防死锁，也可以在死锁发生后解除死锁。但选择被剥夺的进程时要考虑：

- 已经运行了多长时间、还需要多长时间；
- 已经占有多少资源、还需要多少资源；
- 进程优先级与撤销代价；
- 该进程此前被剥夺过多少次。

若系统反复选择同一进程作为受害者，该进程可能一直无法完成，形成饥饿。通常应把被剥夺次数纳入代价，避免无限期牺牲同一进程。

### 第 02 题：哲学家就餐与循环等待【错题】

> **题目：** 在哲学家进餐问题中，若所有哲学家同时拿起左筷子，则发生死锁，因为他们都需要右筷子才能用餐。为了让尽可能多的哲学家可以同时用餐，而且不发生死锁，可以利用信号量 PV 操作实现同步互斥。下列说法中正确的是（　）。
> A. 使用信号量进行控制的方法一定可以避免死锁
> B. 同时检查两支筷子是否可用的方法可以预防死锁，但是会导致饥饿问题
> C. 限制允许拿起筷子的哲学家数量可以预防死锁，它破坏了“循环等待”条件
> D. 对哲学家顺序编号，奇数号哲学家先拿左筷子、再拿右筷子，而偶数号哲学家刚好相反，可以预防死锁，它破坏了“互斥”条件

你的答案：**B**
正确答案：**C**

为什么错：信号量只是实现手段，使用不当仍会死锁，所以 A 错。限制最多 `N-1` 位哲学家同时进入取筷阶段，使所有哲学家各占一支筷子的闭环无法形成，因而破坏循环等待。奇偶号反向取筷同样是破坏循环等待，而不是互斥条件，所以 D 后半句错误。B 把“可能饥饿”说成必然结果，也不成立。

### 第 05 题：死锁的可能原因【错题】

> **题目：** 系统产生死锁的可能原因是（　）。
> A. 独占资源分配不当
> B. 系统资源不足
> C. 进程运行太快
> D. CPU 内核太多

你的答案：**B**
正确答案：**A，独占资源分配不当**

为什么错：资源少会使进程等待，但等待不一定形成死锁。死锁的本质是独占资源的分配次序和等待关系不当，使多个进程形成循环等待。即使资源总量很多，只要分配关系形成闭环，也可能死锁。

### 第 06 题：死锁避免的目标【错题】

> **题目：** 死锁的避免是根据（　）采取措施实现的。
> A. 配置足够的系统资源
> B. 使进程的推进顺序合理
> C. 破坏死锁的四个必要条件之一
> D. 防止系统进入不安全状态

你的答案：**B**
正确答案：**D，防止系统进入不安全状态**

为什么错：死锁避免的代表方法是银行家算法。它在每次资源分配前进行安全性检查，只有分配后仍存在安全序列才允许分配。C 描述的是死锁预防；B 更接近进程调度，并不是死锁避免的定义。

### 第 07 题：资源有序分配破坏哪个条件【错题】

> **题目：** 死锁预防是保证系统不进入死锁状态的静态策略，其解决办法是破坏产生死锁的四个必要条件之一。下列方法中直接破坏了“循环等待”条件的是（　）。
> A. 银行家算法
> B. 一次性分配策略
> C. 剥夺资源法
> D. 资源有序分配策略

你的答案：**C**
正确答案：**D，资源有序分配策略**

为什么错：给资源统一编号并要求进程按递增顺序申请，等待边只能沿编号增大的方向出现，不可能再首尾相接形成环。一次性分配破坏请求并保持；资源剥夺法破坏不剥夺；银行家算法属于死锁避免。

### 第 16 题：资源分配图的定义【错题】

> **题目：** 以下有关资源分配图的描述中，正确的是（　）。
> A. 有向边包括进程指向资源类的分配边和资源类指向进程的申请边两类
> B. 矩形框表示进程，其中圆点表示申请同一类资源的各个进程
> C. 圆圈节点表示资源类
> D. 资源分配图是一个有向图，用于表示某时刻系统资源与进程之间的状态

你的答案：**C**
正确答案：**D**

为什么错：资源分配图中，圆形节点表示进程，矩形节点表示资源类，矩形中的圆点表示资源实例。请求边是“进程 → 资源”，分配边是“资源实例 → 进程”，A 把两种边的方向和名称都说反了。

### 第 20 题：资源剥夺可能导致饥饿【错题】

> **题目：** 某系统采用如下资源分配策略：当一个进程提出资源请求而暂时无法满足时，若当前有其他进程因等待资源而被阻塞，则该进程自行阻塞；若已有因等待资源而被阻塞的进程，则系统检查所有被阻塞的进程，若其中某些进程所占有的资源恰好是当前申请进程所需的，则立即剥夺这些资源并分配给申请进程。该策略可能导致（　）。
> A. 系统死锁
> B. 系统陷入死循环
> C. 进程回退
> D. 进程饥饿

你的答案：**C**
正确答案：**D，进程饥饿**

为什么错：策略允许剥夺资源，能够打破不剥夺条件，但若同一进程反复被选中、资源不断被拿走，它可能长期无法满足继续执行的条件。其他进程仍可推进，因此这种现象是饥饿，而不是所有相关进程相互等待的死锁。题目没有说明进程状态需要回滚，所以不能选 C。

### 第 21 题：资源分配图何时无法判断死锁【存疑但答对】

> **题目：** 系统的资源分配图在下列情况下，无法判断是否处于死锁状态的有（　）。
> I. 出现了环路
> II. 没有环路
> III. 每种资源只有一个，并出现环路
> IV. 每个进程节点至少有一条请求边
> A. I、II、III、IV
> B. I、III、IV
> C. I、IV
> D. 以上答案都不正确

你的答案：**C**
正确答案：**C，I、IV**

你最终判断正确。一般资源分配图有环只能说明可能死锁，因为资源可能有多个实例；每个进程都有请求边也不能说明它们形成闭环，所以 I、IV 都无法直接判断。没有环一定没有死锁；每类资源只有一个实例且出现环路时，一定发生死锁。

### 第 23 题：程序不会死锁，但可能饥饿【错题且存疑】

> **题目：** 下面是并发进程的程序代码，正确的是（　）。

```c
Semaphore x1 = x2 = y = 1;
int c1 = c2 = 0;

P1() {                         P2() {
    while (1) {                   while (1) {
        P(x1);                         P(x2);
        if (++c1 == 1) P(y);           if (++c2 == 1) P(y);
        V(x1);                         V(x2);
        compute(A);                    compute(B);
        P(x1);                         P(x2);
        if (--c1 == 0) V(y);           if (--c2 == 0) V(y);
        V(x1);                         V(x2);
    }                               }
}                              }
```

> A. 进程不会死锁，也不会“饥饿”
> B. 进程不会死锁，但是会“饥饿”
> C. 进程会死锁，但是不会“饥饿”
> D. 进程会死锁，也会“饥饿”

你的答案：**原答案无法从照片中可靠辨认**
正确答案：**B，进程不会死锁，但是可能发生饥饿**

为什么错：`x1`、`x2` 分别保护计数器 `c1`、`c2`，而 `y` 保证 A、B 两类执行者不能同时进入。持有 `y` 的一类执行者退出时不需要另一类的 `x`，不存在首尾相接的资源等待环，因此不会死锁。但若同一类执行者持续到来，使其计数一直不降为 0，`y` 就一直不释放，另一类会长期等待而饥饿。这是典型的 lightswitch（灯开关）模式：能实现类别间互斥，但本身不保证公平。

### 第 24 题：没有同步时并发结果不确定【错题】

> **题目：** 有两个并发进程，对于如下这段程序的运行，正确的说法是（　）。

```text
int x, y, z, t, u;

P1() {                         P2() {
    while (1) {                   while (1) {
        x = 1;                        x = 0;
        y = 0;                        t = 0;
        if x >= 1 then y = y + 1;    if x <= 1 then t = t + 2;
        z = y;                        u = t;
    }                               }
}                              }
```

> A. 程序能正确运行，结果唯一
> B. 程序不能正确运行，可能有两种结果
> C. 程序不能正确运行，结果不确定
> D. 程序不能正确运行，可能死锁

你的答案：**B**
正确答案：**C，程序不能正确运行，结果不确定**

为什么错：两个进程都读写共享变量 `x`，但代码没有任何同步机制。`x=1`、`x=0` 与两个条件判断可以按不同次序交错，条件读取到的值取决于具体调度，因此不能保证程序语义和结果。这里没有互相等待资源的操作，不会死锁。做题时应先判断“存在数据竞争、执行不可控”，不要在缺少原子性和调度约束时武断限定结果种数。

### 第 27 题：死锁定理用于死锁检测【错题且存疑】

> **题目：** 死锁定理是用于处理死锁的（　）方法。
> A. 预防死锁
> B. 避免死锁
> C. 检测死锁
> D. 解除死锁

你的答案：**原答案未清晰写出**
正确答案：**C，检测死锁**

为什么错：死锁定理通过不断化简资源分配图，判断图能否完全化简，从而检测当前系统是否已有死锁。它不改变资源申请规则，所以不是预防；不在每次分配前保证安全状态，所以不是避免；它只负责发现死锁，也不等于撤销进程或剥夺资源等解除操作。

### 第 31 题：解除死锁的方法【错题】

> **题目：** 下列各种方法中，可用于解除已发生死锁的是（　）。
> A. 撤销部分或全部死锁进程
> B. 剥夺部分或全部死锁进程的资源
> C. 降低部分或全部死锁进程的优先级
> D. A 和 B 都可以

你的答案：**A**
正确答案：**D，A 和 B 都可以**

为什么错：死锁已经发生后，可以撤销一个或多个死锁进程，使它们释放资源；也可以剥夺部分进程的资源并分配给其他进程，打破等待闭环。单纯降低优先级不会释放资源，也不能解除已经形成的死锁。

### 第 39 题：死锁避免与死锁检测的区别【错题】

> **题目：**【2015 统考真题】若系统 S1 采用死锁避免方法，S2 采用死锁检测方法。下列叙述中，正确的是（　）。
> I. S1 会限制用户申请资源的顺序，而 S2 不会
> II. S1 需要进程运行所需的资源总量信息，而 S2 不需要
> III. S1 不会给可能导致死锁的进程分配资源，而 S2 会
> A. 仅 I、II
> B. 仅 II、III
> C. 仅 I、III
> D. I、II、III

你的答案：**D**
正确答案：**B，仅 II、III**

为什么错：I 错，把资源按统一顺序申请是“死锁预防”的资源有序分配法，不是死锁避免的必然要求。II 对，银行家算法需要事先知道进程的最大资源需求，而检测算法根据当前分配和请求状态判断即可。III 对，避免算法会拒绝可能使系统进入不安全状态的分配；检测策略允许资源按请求分配，因此可能让死锁形成，再进行检测和解除。

## 四、做题判断流程

遇到死锁题时，按以下顺序判断：

1. 题目问的是“还没发生时防止”，还是“已经发生后处理”？
2. 若在发生前处理，是直接破坏必要条件，还是每次分配前检查安全状态？
3. 若给出资源分配图，资源是单实例还是多实例？图中是否有环？
4. 若使用银行家算法，先计算 `Need = Max - Allocation`，再寻找安全序列。
5. 若给出同类资源数量，代入 `m >= n(k-1)+1` 检查最坏情况。
6. 若给出并发代码，分别检查循环等待和长期不公平，区分死锁与饥饿。
7. 若问解除方法，确认措施是否真正释放或重新分配了资源。

快速归类：

```text
破坏四个必要条件之一      → 死锁预防
分配后仍保持安全状态      → 死锁避免
银行家算法                → 死锁避免
资源分配图化简、死锁定理  → 死锁检测
撤销进程、剥夺资源        → 死锁解除
资源统一编号、顺序申请    → 预防循环等待
一次申请全部资源          → 预防请求并保持
允许强制收回资源          → 破坏不剥夺
无环                      → 一定没有死锁
有环且资源均为单实例      → 一定死锁
有环且存在多实例资源      → 可能死锁，继续检测
不安全                    → 可能死锁，不代表已经死锁
某进程长期得不到资源      → 饥饿
一组进程相互等待无法推进  → 死锁
```
